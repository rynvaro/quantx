## 一、三份文档的关系分析

当前目录下存在三份文档：

| 文档 | 定位 |
|------|------|
| `quantx_design.md` | 工程架构视角，描述如何建立完整系统 |
| `calm_trigger_v0.md` | 市场哲学原始记录，弹簧模型的最初直觉 |
| `calm_trigger_v1.md` | 信号逻辑视角，弹簧模型的系统化设计 |

**核心结论：三份文档不是竞争关系，而是互补关系。**

`quantx_design.md` 的特征工程是把多时间框架特征"平铺拼接"输入模型，模型需要自己学习特征之间的协同规律。`calm_trigger_v1.md` 的 CTI 是一个**显式跨时间尺度交叉特征**，直接把"背景平静 + 短期加速 + 趋势方向对齐"的组合效应编码为一个数，相当于把市场哲学直接告诉模型，在样本量有限时能显著降低模型学习难度。

**综合方式**：
- 系统架构 / 数据流 / 模型训练 / 回测 / 执行 → 完全沿用 `quantx_design.md`
- 特征体系 → 在完整特征基础上额外加入 CTI 作为显式交叉特征
- 滑窗步长 → 采用 `calm_trigger_v1.md` 提出的 5min 步长
- 标签定义 → 两文档一致，用区间最高点涨幅

## 二、弹簧模型的已有先例及指标细化建议

### 2.1 弹簧模型并非独创

"压缩 → 触发 → 释放"的结构在量化领域有几种已知形式化：

| 策略名称 | 核心逻辑 |
|---------|---------|
| Bollinger Band Squeeze（TTM Squeeze） | 布林带收窄到 Keltner 通道内部，判断为高度压缩，等待方向释放 |
| NR7 | 识别7根K线内最窄的价格区间，预测即将突破 |
| VCP（Mark Minervini） | 系统化的波动率收缩形态，寻找爆发前的积累期 |
| Wyckoff Spring | 价格在支撑位下方假破后快速拉回，积累阶段结束的标志，字面即"弹簧" |

**独创部分**在于：把弹簧压缩（calm_depth）和触发加速（trigger_score）显式量化后做乘法，构造 CTI 作为机器学习特征，而不是像传统技术分析那样依赖肉眼形态识别。这个工程化的方式是原创的设计。

### 2.2 触发层的向内细化建议

**不建议往秒级延伸**（5秒 / 10秒加速度），原因：
- 币安 K 线最小粒度是 1 分钟，秒级数据需要从逐笔成交自行聚合，工程复杂度大幅提升
- 对于 15 分钟预测目标，5 秒内的价格抖动 90% 以上是买卖价差的来回跳动（Bid-Ask Bounce），不是真实方向性信号
- 时间尺度不匹配：5 秒与 15 分钟跨越 180 倍时间尺度，相关性极弱

**推荐向内细化的正确做法**：在 1m K 线基础上增加不同窗口的加速度：

| 新增指标 | 窗口 | 意义 |
|---------|------|------|
| roc_accel_3m | 3根K线 ROC 的差分 | 中短期加速 |
| roc_accel_1m | 1根K线 ROC 的差分 | 最近一根的即时加速 |

三个窗口（5m / 3m / 1m）的加速度方向一致且递增，说明触发正在向更短周期扩散，是更强的信号。全部基于 1m K 线，数据干净无额外成本。

### 2.3 周末数据的处理建议

加密市场 24/7 连续交易，但周末行情有显著差异：

| 维度 | 周末特征 |
|------|---------|
| 流动性 | 更低，机构参与度下降 |
| 滑点 | 更高 |
| 波动模式 | 通常更低，但偶有极端波动（无机构对冲） |
| 弹簧模型有效性 | 触发后延续性较弱，缺乏机构跟进 |

三种方案对比：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 直接删除周末数据 | 简单，排除低质量样本 | 损失约 28% 数据量 |
| 加 `day_of_week` + `hour_of_day` 特征 | 保留全部数据，让模型自己学 | 初期效果不确定 |
| 单独训练周末模型 | 最精准 | 维护成本翻倍，周末样本本身就少 |

**推荐路径**：
1. 初期加两个特征 `day_of_week`（0-6）和 `hour_of_day`（0-23），让模型学时间规律，工程成本最低
2. 训练后用 SHAP 分析 `day_of_week` 的贡献，如果周末 Precision 显著低于工作日，再单独处理
3. 执行层兜底：周六 / 周日 UTC 00:00 到 16:00（流动性最低时段）不触发交易，即使模型输出高概率也不执行

## 三、模型选择建议

### 3.1 推荐路径：三阶段递进

```
阶段一：XGBoost（flatten 特征向量）
  目标：验证特征有效性，特别是 CTI 的 SHAP 贡献
  通过条件：IC > 0.05，Precision > 55%

阶段二：LightGBM
  XGBoost 的高效替代，训练速度更快
  对大样本和高维特征更友好，迁移成本接近零

阶段三：Transformer（保留序列结构）
  输入改为 sequence 形式（30×N 矩阵）
  需要 5 年以上历史数据（样本量 > 50 万）
  只在阶段二验证特征体系有效后才升级
```

### 3.2 各阶段模型对比

| 维度 | XGBoost | Transformer |
|------|---------|-------------|
| 样本量需求 | 1-10 万足够 | 通常需要 10 万+ 才发挥优势 |
| 调参难度 | 低，参数直观 | 高，需要 warmup / schedule 等 |
| 训练速度 | 分钟级 | 小时级（CPU）|
| 可解释性 | SHAP + feature importance，直接看特征贡献 | 黑盒，难解释 |
| 过拟合风险 | 较低（内置正则）| 较高（参数量大）|
| 跨时间框架交互 | 不擅长（特征当独立列处理）| 擅长（注意力机制天然处理序列）|

**跳过阶段一直接上 Transformer 的风险**：无法区分是"特征无价值"、"模型未训练好"还是"数据量不足导致欠拟合"三种失败原因。XGBoost 先跑通，才能把这三个问题解耦。

### 3.3 XGBoost 的输入形式

每个时间框架取**最后一根 K 线**的指标值（已经隐含历史信息，因为 EMA / RSI 等本身就是历史数据的压缩），flatten 成一维特征向量输入。CTI 作为标量特征直接加入向量，SHAP 分析可以直接评估其贡献。

## 四、交易所接口可行性分析

### 4.1 数据可行性总览

| 数据类别 | 可行性 | 获取方式 |
|---------|-------|---------|
| OHLCV + taker buy（5个时间框架）| ✅ 完全可行 | Klines REST API，换 interval 参数 |
| 成交笔数（number of trades）| ✅ 完全可行 | Klines 接口直接返回 |
| 资金费率（Funding Rate）| ✅ 可行，仅永续合约 | 专用 fundingRate 接口 |
| 逐笔成交（用于 IAI 指标）| ✅ 可行但量大 | aggTrades / trades 接口 |
| 历史订单簿快照 | ❌ 不可行 | 交易所不存储，只有实时快照 |
| 期权隐含波动率 | ❌ 可忽略 | 加密期权流动性差，数据质量低 |

**实施结论**：最精简起步方案为只用 Klines 数据（5个时间框架）+ 资金费率，覆盖文档中 90% 以上指标的原始数据需求。订单簿和 IAI 可在第二阶段引入。

### 4.2 各接口历史数据深度

| 数据类型 | Binance 历史深度 | Bybit 历史深度 | 备注 |
|---------|--------------|--------------|------|
| 1m Klines（BTC/USDT）| 约 2017 年 8 月至今，约 **8-9 年** | 约 2019-2020 年至今，约 **5-6 年** | 主流币对数据最全 |
| 5m / 15m / 1h / 4h Klines | 同上，数据点数成比例减少 | 同上 | |
| 山寨币 Klines | 从上市日起，深度不一 | 同左 | 新币历史数据少，不适合训练 |
| 资金费率 | 从合约上市日起（BTC 约 2019 年）| 同左 | 8 小时一次 |
| aggTrades（逐笔成交）| REST 接口仅支持最近约 **1 个月** | 类似 | 长期历史需用 Binance Data Portal 或第三方 |
| 订单簿快照 | **无历史数据** | **无历史数据** | 只有实时 |

**Binance Data Portal 补充说明**：Binance 官方提供 [data.binance.vision](https://data.binance.vision) 可下载更完整的历史数据（Klines / aggTrades / bookTicker），数据以月度压缩包形式存放，下载后可本地构建完整历史数据库。BTC/USDT 1m K 线从 2017 年至今约 **420 万条记录**，压缩后约 200MB，完全可以本地存储。

**训练数据量规划**（以 BTC/USDT 为例）：

| 时间范围 | 1m K 线条数 | 5min 滑窗样本量 | 备注 |
|---------|-----------|--------------|------|
| 1 年 | ~525,600 | ~10 万 | 基础验证够用 |
| 3 年 | ~1,576,800 | ~30 万 | 涵盖牛熊完整周期 |
| 5 年 | ~2,628,000 | ~50 万 | Transformer 阶段推荐 |

**建议**：初期用 3 年历史数据（2022-2025），涵盖一个完整的牛熊周期，对模型泛化性更有保障。

## 五、订单簿深度对整体系统的影响评估

### 5.1 订单簿能提供什么信息

| 信号类型 | 来源 | 能用替代品吗 |
|---------|------|-----------|
| 即时供需不平衡（OBI） | 买盘深度 vs 卖盘深度 | 部分可用 taker_buy_ratio 替代 |
| 大单墙（支撑/阻力）| 异常大的挂单堆积 | 无直接替代 |
| 冰山订单（隐藏大单）| 分析连续成交模式 | 部分可用 IAI 替代 |
| 订单撤销速率 | 频繁挂撤单行为 | 无替代 |

### 5.2 订单簿缺失的实际影响

**对 Model-15m 的影响是有限的**，而非关键性缺口，原因：

1. **预测窗口较长（15 分钟）**：订单簿在 15 分钟内会被多次刷新，当前时刻的挂单分布对 15 分钟后的价格的直接预测力较弱
2. **taker_buy_ratio 已经捕捉了最核心的供需信息**：实际成交比挂单更能反映真实意愿，挂单可以随时取消，成交不能
3. **大单墙信息间接体现在价格行为中**：价格在关键位置的停顿、反复测试等行为，会反映在多时间框架的 ROC / ATR / MACD 指标里

**量化估计**（基于学术研究的近似参考）：

| 特征来源 | 对 15m 预测 Precision 的贡献估计 |
|---------|-------------------------------|
| 多时间框架 OHLCV + 技术指标 | 主体贡献，约 80-85% |
| taker_buy_ratio（买压代理）| 约 8-10% |
| 订单簿 OBI（如可用）| 约 **3-6%** |
| 订单簿大单墙（如可用）| 约 **2-4%** |

> 注：以上为数量级估计，实际贡献需通过 SHAP ablation 实测验证。

### 5.3 结论

**订单簿缺失对系统的影响约为 5-10% 的 Precision 提升空间损失**，是可接受的权衡。更重要的是，即使将来想引入订单簿特征，也只能从当下起开始实时采集并存储——这意味着需要先建立一个订单簿快照采集服务（每秒或每5秒存一次深度快照），积累 3-6 个月后才有足够的历史数据用于训练。

**建议**：
- 第一阶段：完全不使用订单簿，用 taker_buy_ratio 和 IAI（aggTrades）替代
- 第二阶段：若系统上线，考虑同步启动订单簿快照采集服务，为未来的第三版特征体系积累数据
- 永远不值得为了订单簿特征去购买第三方历史数据（价格昂贵且质量参差不齐）
